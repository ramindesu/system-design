# فصل ۱۶ — ادامهٔ یادگیری با اندازه‌گیری

**عنوان کتاب:** The Learning Continues · صفحات ۲۶۴ تا ۲۶۶ PDF.

این فصل فهرست مسیرهای مطالعهٔ معماری واقعی است؛ الگوریتم تازه‌ای معرفی نمی‌کند. تمرین کدنویسی زیر افزودهٔ این جزوه است: فرض‌های فصل‌های قبل را به آزمایش تبدیل کنیم. هدف این نیست که یک شرکت بزرگ را با چند فایل بازسازی کنیم؛ باید بفهمیم هر ابزار کدام محدودیت مشاهده‌شده را حل می‌کند.

## برنامهٔ تمرین با پروژهٔ همراه

1. **Baseline:** پروژهٔ فصل ۱ را بدون Replica و Cache مشترک اجرا کن؛ رفتار و قرارداد API را بفهم.
2. **Read Routing:** قیمت Primary را عوض کن و Snapshot را ثابت نگه دار؛ نتیجهٔ دو اتصال را مقایسه کن.
3. **Cache:** یک Read تکراری بزن؛ سپس تغییر قیمت و Invalidation پس از Commit را بررسی کن.
4. **Concurrency:** روی PostgreSQL با دو اتصال مستقل تغییر همزمان را امتحان کن؛ تست SQLite کافی نیست.
5. **Queue:** بعد از Commit و قبل از Publish برنامه را متوقف کن؛ تفاوت Callback و Outbox را ببین.
6. **Failure:** برای سرویس‌های آزمایشی خودت Timeout و قطع اتصال ایجاد کن و رفتار Fallback/Retry را بررسی کن.

## اندازه‌گیری Query در Django

این کد را در Shell پروژهٔ آزمایشگاهی فصل اول اجرا کن؛ `CaptureQueriesContext` ابزار Debug/Test است و برای ثبت همهٔ SQLهای Production پیشنهاد نمی‌شود.

```python
from django.db import connections
from django.test.utils import CaptureQueriesContext
from django.core.cache import cache
from catalog.services import get_book

cache.clear()
with CaptureQueriesContext(connections["default"]) as cold:
    get_book(1)
with CaptureQueriesContext(connections["default"]) as warm:
    get_book(1)
print("cold queries:", len(cold))  # expected: 1
print("warm queries:", len(warm))  # expected: 0
```

اگر تعداد Query تغییر کرد، علت را در مسیر واقعی پیدا کن؛ تعداد کم Query به‌تنهایی سرعت را تضمین نمی‌کند. یک Query بدون Index روی میلیون‌ها رکورد می‌تواند بدتر از چند Query کوچک باشد. برای Load Test، ترکیب Read/Write، Cache سرد/گرم و حجم دادهٔ واقعی‌نما را جدا تعریف کن.

## برای هر تغییر یک گزارش کوتاه

بنویس: «فرض من این بود که…؛ قبل از تغییر p95 برابر… بود؛ بعد از تغییر… شد؛ تعداد خطا… بود؛ هزینه و محدودیت تازه… است.» فقط سرعت را نبین؛ در Replica ممکن است Latency بهتر ولی تازگی داده بدتر شود. در Queue ممکن است زمان پاسخ API کم شود ولی کاربر دقیقه‌ها منتظر نتیجه بماند.

از منابع رسمی هر فصل برای جزئیات API و از معماری‌های واقعی برای تصمیم و Tradeoff استفاده کن. لینک‌ها و آمار کتاب مربوط به زمان انتشار آن‌اند؛ آن‌ها را به‌عنوان وضعیت امروز شرکت‌ها یا سرویس‌ها در نظر نگیر.

**تمرین پایانی:** یک قابلیت «ثبت سفارش و اعلان ایمیل» طراحی کن و توضیح بده: DB اصلی کدام است؟ چه Readهایی می‌توانند Replica باشند؟ Transaction تا کجا ادامه دارد؟ Event چگونه پایدار می‌شود؟ اگر Task دوباره اجرا شد چه اتفاقی می‌افتد؟

**پاسخ راهنما:** سفارش و Outbox در یک Transaction Primary ثبت شوند؛ موجودی با کنترل همزمانی بررسی شود؛ Worker اعلان را با Retry محدود بفرستد؛ Idempotency متناسب با Provider طراحی شود؛ خواندن حساس از Primary و نتیجهٔ نهایی از وضعیت ثبت‌شده بیاید.

## پروژهٔ جمع‌بندی: سفارش و Event در یک Transaction

آزمایشگاه مستقل این فصل سه Model دارد: `Stock`، `Order` و `OrderEvent`. Scope «ثبت سفارش با رزرو موجودی و ثبت قصد اعلان» است؛ پول جابه‌جا نمی‌شود و اتصال واقعی ایمیل نداریم. در فصل ۳ رزرو و در فصل ۱۰ Outbox را جدا دیدیم؛ اینجا آن‌ها را در یک مرز Transaction کنار هم می‌گذاریم.

```python
import uuid
from demo.services import checkout, publish_events

key = uuid.uuid4()
order = checkout(stock.pk, user.pk, quantity=1, request_id=key)
same = checkout(stock.pk, user.pk, quantity=1, request_id=key)
queue = []
publish_events(queue.append)
print(order.pk == same.pk, queue)
```

یک سفارش و یک Event ساخته می‌شود، موجودی یک بار کم می‌شود و Publish به صف تمرینی انجام می‌شود. اگر ساخت Event شکست بخورد، موجودی و Order هم Rollback می‌شوند. این اصل مهم است: اضافه کردن Outbox بعد از Commit سفارش، همان شکاف از دست رفتن Event را دوباره ایجاد می‌کند.

## از پروژهٔ جمع‌بندی چه نتیجه‌ای بگیریم؟

`checkout` از Primary و قفل همان Stock استفاده می‌کند. درخواست Retry Payload را با سفارش قبلی مقایسه می‌کند. سفارش موفق فقط وقتی ایجاد می‌شود که Event پایدار هم ثبت شده باشد. `publish_events` تک Publisher است و ممکن است در شکاف Publish/Update تکرار کند؛ مصرف‌کنندهٔ واقعی هنوز به Idempotency فصل ۱۰ نیاز دارد.

کد جمع‌بندی همهٔ سیستم را نمی‌سازد. Payment، لغو سفارش، رزرو منقضی، چند قلم سفارش، Tax، Delivery و Refund جزء Scope نیستند. اگر این موارد اضافه شدند، Transaction، State Machine و سیاست Retry را دوباره بررسی کن؛ نمی‌توان به همان موفقیت تست ساده استناد کرد.

## برنامهٔ اجرای منظم فصل‌ها

برای هر فصل، ابتدا مسئله را با یک مثال توضیح بده؛ سپس مسیر موفق را در Shell اجرا کن؛ بعد یک شکست مشخص بساز؛ در آخر انتخاب خودت را با یک Alternative مقایسه کن. وقتی می‌توانی بدون دیدن کد توضیح بدهی «این Query کجا اجرا می‌شود و چرا»، از حفظ کردن اسم ابزارها عبور کرده‌ای.

هر آزمایش را با دادهٔ ورودی، Backend، نسخه، خروجی و محدودیت ثبت کن. مثلاً «تعداد Query سه Purchase از ۴ به ۱ رسید روی SQLite» یک نتیجهٔ قابل بررسی است؛ «این سیستم میلیون‌ها کاربر را پشتیبانی می‌کند» از آن آزمایش نتیجه نمی‌شود. برای ادعای ظرفیت باید Load Test با داده و همزمانی مناسب داشته باشی.

## ترتیب مطالعهٔ منابع واقعی

از معماری‌های معرفی‌شده در پایان کتاب، یک مثال انتخاب کن و پنج سؤال پاسخ بده: مسئلهٔ اصلی چه بوده؟ کدام قید باعث این تصمیم شده؟ مرجع معتبر داده کجاست؟ شکست و بازیابی چگونه انجام می‌شود؟ اگر مقیاس یک‌صدم بود، چه چیزهایی ساده‌تر می‌شد؟ این روش از کپی کردن Diagram به پروژه مفیدتر است.

برای APIهای Django به لینک رسمی نسخهٔ همین پروژه مراجعه کن. مقالهٔ معماری تاریخ دارد؛ عدد کاربران، Latency و انتخاب سرویس آن مربوط به همان شرایط است. برای خرید یا Deploy واقعی باید وضعیت و هزینهٔ امروز جدا بررسی شود؛ این مجموعه هیچ سرویس خارجی ایجاد نمی‌کند.

## تمرین نهایی با پاسخ مرحله‌ای

1. Request ID ثابت را دو بار به `checkout` بده. — یک Order، یک Event و یک کاهش موجودی.
2. ساخت Event را با خطا متوقف کن. — هیچ Order موفقی باقی نماند و موجودی همان مقدار قبل باشد.
3. Publisher Callback را خراب کن. — Event هنوز Pending باشد؛ اجرای بعدی بتواند آن را منتشر کند.
4. آیا Publish موفق یعنی ایمیل رسیده؟ — خیر؛ فقط مرحلهٔ بعدی را فعال کرده‌ایم. Acceptance/Delivery جداست.
5. اگر دیتابیس Replica داریم، کدام Readها را منتقل می‌کنی؟ — فهرست عمومی با تأخیر مجاز؛ تصمیم موجودی و تأیید سفارش از Primary.

## معیار پایان مطالعهٔ این مجموعه

اگر می‌توانی مدل داده، مسیر درخواست، Consistency، رفتار Retry و نقطهٔ خرابی هر مثال را توضیح بدهی و تست آن را اجرا کنی، پایهٔ عملی خوبی ساخته‌ای. قدم بعد ساختن یک پروژهٔ واقعی کوچک با نیاز مشخص و اندازه‌گیری آن است. انتخاب معماری باید از مشاهده و قید بیاید، نه از تعداد سرویس‌ها.

**مرز تست:** جمع‌بندی محلی Reservation/Outbox بررسی می‌شود؛ سفارش واقعی، پرداخت و سیستم Production ایجاد نشده‌اند.

## شروع عملی این فصل

پوشهٔ `lab` همین فصل یک پروژهٔ مستقل است. فایل `lab/README.md` روش نصب و اجرا را توضیح می‌دهد. پس از نصب Django و اجرای Migration، دستور `python demo_script.py` مثال اصلی را با دادهٔ تمرینی اجرا می‌کند؛ `python manage.py test` هم تست‌های رفتاری را اجرا می‌کند. در این مسیر فقط محیط محلی استفاده می‌شود و حساب سرویس خارجی لازم نیست. کدهای Connector اختیاری در متن، نیازهای جدا دارند.

**نتیجهٔ بررسی:** 3 تست این فصل با SQLite پاس شده است. این نتیجه، عملکرد کلاستر، Provider واقعی یا تست همزمانی PostgreSQL نیست.
