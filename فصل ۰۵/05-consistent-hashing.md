# فصل ۵ — تقسیم داده با Consistent Hashing

**عنوان کتاب:** Design Consistent Hashing · صفحات ۷۱ تا ۸۶ PDF.

## مشکل تقسیم ساده

اگر مقصد کلید را با `hash(key) % N` انتخاب کنیم، تغییر تعداد سرور از ۳ به ۴ مقصد بسیاری از کلیدها را عوض می‌کند. در Cache، این اتفاق می‌تواند Miss زیاد و فشار ناگهانی بر DB ایجاد کند. در Storage، داده باید واقعاً جابه‌جا شود؛ فقط تغییر فرمول کافی نیست.

Consistent Hashing کلیدها و سرورها را روی یک حلقهٔ عددی قرار می‌دهد. مقصد کلید اولین سرور در جهت حرکت حلقه است. اضافه شدن سرور فقط بخشی از محدوده‌ها را تغییر می‌دهد. برای تعادل بهتر، هر سرور با چند **Virtual Node** نمایندگی می‌شود. این Virtual Nodeها Process واقعی نیستند.

## کد Python قابل اجرا

`HashRing` در `examples/algorithms.py` از SHA-256 و Binary Search استفاده می‌کند:

```python
from demo.algorithms import HashRing

ring = HashRing(["cache-a", "cache-b", "cache-c"], replicas=64)
print(ring.owner("book:123"))

larger_ring = HashRing(["cache-a", "cache-b", "cache-c", "cache-d"])
keys = [f"book:{i}" for i in range(1000)]
moved = sum(ring.owner(k) != larger_ring.owner(k) for k in keys)
print("moved:", moved)
```

ساخت حلقه تقریباً متناسب با تعداد نقطه‌ها و مرتب‌سازی آن‌هاست؛ پیدا کردن مقصد با Binary Search لگاریتمی است. از `hash()` داخلی Python برای مقصد مشترک بین Processها استفاده نکن؛ خروجی Hash رشته‌ها می‌تواند بین اجراها متفاوت باشد.

## کاربرد در Django

در یک Cache سفارشی با اتصال‌های جدا، خروجی `owner` را به Client متناظر وصل می‌کنی. همهٔ Workerها باید Membership و نسخهٔ حلقهٔ یکسان داشته باشند. مثلاً اگر Worker اول سه سرور ببیند و Worker دوم چهار سرور، ممکن است دربارهٔ محل داده اختلاف داشته باشند.

با Redis Cluster، Sharding داخلی خودش مدیریت می‌شود؛ این حلقه را بدون دلیل روی آن سوار نکن. برای دیتابیس Shardشده نیز انتخاب مقصد فقط یک جزء است: Replication، انتقال داده، Backfill، Routing هنگام Migration و کنترل نسخهٔ نقشه لازم‌اند.

## خطاهای رایج

Virtual Node بیشتر توزیع را معمولاً بهتر می‌کند اما **Hot Key** را حل نمی‌کند. اگر یک کتاب ۸۰٪ ترافیک را بگیرد، مقصد آن هنوز داغ می‌ماند. می‌توان دادهٔ خواندنی را Replicate کرد یا با سیاست Cache مناسب پخش کرد. همچنین Consistent Hashing خودش تشخیص خرابی یا کپی داده انجام نمی‌دهد.

**تمرین:** وقتی `cache-d` اضافه می‌شود کدام کلیدها جابه‌جا می‌شوند؟ **پاسخ:** فقط کلیدهایی که سرور جدید بین موقعیت آن‌ها و مقصد قبلی‌شان قرار گرفته است. تست بسته بررسی می‌کند هر کلید جابه‌جاشده بعد از اضافه شدن `c`، مقصدش `c` باشد.


## یک حلقهٔ کوچک روی کاغذ

برای فهم الگوریتم، به‌جای SHA-256 یک فضای ۰ تا ۹۹ تصور کن. سرورها در ۲۰، ۵۰ و ۸۰ هستند. کلید در ۳۵ به سرور ۵۰ می‌رود؛ کلید در ۹۰ دور حلقه می‌چرخد و به ۲۰ می‌رود. سرور جدید در ۴۰، فقط کلیدهای بعد از ۲۰ تا ۴۰ را از مقصد قبلی می‌گیرد. کلید ۷۰ همچنان به ۸۰ می‌رود.

در کد واقعی Hash دامنهٔ بسیار بزرگ‌تری دارد. لیست نقاط مرتب می‌شود و `bisect_left` نخستین نقطهٔ مساوی یا بزرگ‌تر را پیدا می‌کند. اگر اندیس از انتهای لیست گذشت، به صفر برمی‌گردیم؛ `% len(points)` برای Wrap-around لیست است، نه همان تقسیم سادهٔ `hash(key) % number_of_servers` که مشکل ابتدای فصل را داشت.

## کد کامل حلقه کجاست؟

در `lab/demo/algorithms.py` پیاده‌سازی کامل `HashRing` وجود دارد. هر Node با ۶۴ نقطه وارد حلقه می‌شود. ورودی Nodeها مرتب و Deduplicate می‌شود تا دو Worker با ترتیب ورودی متفاوت، حلقهٔ یکسان بسازند. ترتیب نام‌ها، تعداد Virtual Node و تابع Hash بخشی از قرارداد هستند؛ تغییر هرکدام می‌تواند Mapping را عوض کند.

`replicas=64` در این کلاس تعداد Virtual Node است. این اسم **تعداد کپی داده** را تعیین نمی‌کند. برای کاهش ابهام در محصول واقعی آن را `virtual_nodes` بنام. داشتن چند نقطه روی حلقه باعث ذخیره شدن چند نسخه از همان کلید نمی‌شود.

## Django: وصل کردن حلقه به Cache Alias

آزمایشگاه چهار Cache مستقل LocMem دارد. `ShardedCache` کلید را به یک Alias هدایت می‌کند و با API معمول Django مقدار را ذخیره می‌کند:

```python
from demo.services import ShardedCache

client = ShardedCache(["cache-a", "cache-b", "cache-c"])
client.set("book:123", {"price": "150.00"}, timeout=30)
print(client.get("book:123"))
```

نمونهٔ داخلی `caches[ring.owner(key)]` را انتخاب می‌کند. این Client برای فهم Routing است؛ LocMemهای آن بین Processها مشترک نیستند. در نسخهٔ واقعی، Aliasها می‌توانند به Cache Serverهای جدا اشاره کنند. پس از تغییر Membership، کلید جابه‌جاشده ممکن است Miss شود؛ از Primary دوباره پر می‌شود. برای Storage پایدار باید داده منتقل شود، چون «Miss و پر کردن از مرجع دیگر» همیشه ممکن نیست.

## سنجش تعادل و جابه‌جایی

هزار یا ده‌هزار کلید نمونه بساز، تعداد هر مقصد را با `Counter` حساب کن و قبل/بعد اضافه کردن Node تعداد کلیدهای تغییرکرده را بشمار. Virtual Node بیشتر معمولاً پراکندگی را بهتر می‌کند، ولی نتیجه برای تعداد کم کلید نوسان دارد؛ ادعای درصد دقیق ثابت نکن. حتی توزیع تعداد کلید مساوی، لزوماً توزیع QPS یا Byte مساوی نیست.

اگر یکی از سرورها ظرفیت دو برابر دارد، می‌توان Virtual Node بیشتری به آن داد؛ این پیاده‌سازی آموزشی وزن ندارد. اگر یک کلید بسیار داغ است، افزایش Virtual Node آن کلید را چندتکه نمی‌کند. Cache خواندنی Replicateشده، Request Coalescing و طراحی خاص Hot Key گزینه‌های جدا هستند.

## ورود و خروج امن Node

Membership جدید باید Version داشته باشد و Workerها زمان گذار مشخصی داشته باشند. برای DB، معمولاً ابتدا Backfill، سپس همگام‌سازی تغییرهای تازه، بعد تغییر Routing و در نهایت Cleanup داریم. در فاصلهٔ گذار ممکن است Dual-read/Write لازم شود؛ باید دربارهٔ شکست و تکرار آن تصمیم بگیری. این مراحل با Consistent Hashing خودکار ساخته نمی‌شوند.

## تمرین و پاسخ

1. ترتیب ورودی Nodeها را عوض کن. — مقصد کلیدها باید ثابت بماند؛ Sorting داخل کلاس این را برقرار می‌کند.
2. Node جدید اضافه کن. — هر کلید تغییرکرده باید به Node جدید برود، نه بین Nodeهای قدیمی بی‌دلیل جابه‌جا شود.
3. یکی از Nodeها را حذف کن. — کلیدهای مقصد آن جابه‌جا می‌شوند؛ بقیه باید ثابت بمانند.
4. اگر Mapping درست است ولی داده نیست، مشکل چیست؟ — الگوریتم محل را انتخاب کرده ولی Migration/Replication داده هنوز انجام نشده است.
