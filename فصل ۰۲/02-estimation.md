# فصل ۲ — تخمین ظرفیت قبل از طراحی

**عنوان کتاب:** Back-of-the-envelope Estimation · صفحات ۳۴ تا ۴۱ PDF.

## مسئله و روش فکر کردن

«یک میلیون کاربر» عدد کافی برای خرید سرور نیست. چند نفر روزانه فعال‌اند؟ هر نفر چند Read و Write دارد؟ اندازهٔ هر رکورد چقدر است؟ چه مدت نگهش می‌داریم؟ فرض‌ها را جدا از نتیجه بنویس؛ بعداً می‌توانی آن‌ها را با دادهٔ واقعی اصلاح کنی.

برای فروشگاه فرض کنیم ۱۰۰ هزار کاربر روزانه فعال داریم؛ هرکدام ۲۰ بار محصول می‌بینند و میانگین ۰٫۱ سفارش دارند. متوسط Read حدود ۲۳ درخواست در ثانیه و متوسط Write حدود ۰٫۱۲ است. با ضریب Peak برابر ۵، حدود ۱۱۶ Read در ثانیه داریم. این اعداد فرضی‌اند؛ ظرفیت واقعی Django را Load Test تعیین می‌کند.

## پیاده‌سازی با Python

در `examples/algorithms.py` تابع `capacity` ورودی‌ها را به QPS و Bytes تبدیل می‌کند:

```python
from demo.algorithms import capacity

result = capacity(
    dau=100_000, reads_per_user=20, writes_per_user=0.1,
    bytes_per_write=2000, days=365, peak_factor=5,
)
print(result)
# read_qps ≈ 23.15, peak_read_qps ≈ 115.74
# raw_storage_bytes = 7_300_000_000
```

عدد Storage بالا فقط Payload خام است؛ Index، فضای آزاد، WAL، نسخه‌های قدیمی، Backup، Replica و عکس‌ها داخل آن نیستند. اگر یک عکس ۱ MB باشد، معمولاً از متن سفارش خیلی بزرگ‌تر است. `MB` ده‌دهی و `MiB` دودویی را قاطی نکن: ۱ MiB برابر ۱۰۴۸۵۷۶ Byte است.

## ربط به Django

QPS مربوط به HTTP لزوماً QPS دیتابیس نیست. یک View ممکن است ۵۰ Query بزند. اگر صفحهٔ سفارش‌ها برای هر سفارش جدا کاربر را بخواند، N+1 ایجاد می‌شود؛ `select_related("user")` برای ForeignKey می‌تواند خواندن را با Join انجام دهد. برای روابط چندتایی، `prefetch_related` معمولاً Queryهای جدا ولی دسته‌ای می‌زند.

برای تخمین اتصال‌ها، تعداد Processها، Threadها و اتصال باز هرکدام را حساب کن. برای درخواست همزمانِ در حال اجرا، تقریب `concurrency ≈ throughput × response_time` در حالت پایدار کمک می‌کند؛ صف انتظار و Peak را جدا اندازه بگیر. ۲۰۰ درخواست در ثانیه با زمان پاسخ ۰٫۵ ثانیه تقریباً ۱۰۰ درخواست همزمان است.

## Latency و Availability

جدول Latency کتاب مربوط به زمان انتشار آن است؛ عددهایش معیار قطعی سخت‌افزار امروز نیستند. از آن تفاوت مرتبهٔ هزینهٔ حافظه، دیسک و شبکه را یاد بگیر و پروژهٔ خودت را اندازه بگیر. در یک سال ۳۶۵روزه، ۹۹٫۹٪ Availability تقریباً ۸ ساعت و ۴۶ دقیقه بودجهٔ قطعی می‌دهد. تعریف موفقیت، بازهٔ اندازه‌گیری و استثناهای SLA هم مهم‌اند.

**تمرین:** اگر ۹۰٪ Readها Cache Hit شوند، DB تقریباً چند Read دریافت می‌کند؟ **پاسخ:** در مثال Peak حدود ۱۱٫۶ Read/s، اگر هر Cache Miss یک Query داشته باشد. حمله، Cache سرد و Stampede این فرض را تغییر می‌دهند.

## حل قدم‌به‌قدم یک مسئلهٔ واقعی‌نما

فرض‌ها را در چهار گروه بنویس: ترافیک، اندازه، مدت نگهداری و هدف پاسخ. در مثال ما `100000 × 20 = 2000000` Read روزانه داریم. تقسیم بر ۸۶۴۰۰، QPS متوسط را می‌دهد. ضریب Peak را از روی یک بازهٔ واقعی انتخاب می‌کنیم؛ ضریب ۵ صرفاً فرض تمرین است. اگر همهٔ مشتریان ساعت ۹ صبح وارد شوند، میانگین روزانه برای ظرفیت کافی نیست.

هر سفارش ۲۰۰۰ Byte فرض شده است. `100000 × 0.1 × 2000 × 365` برابر ۷٫۳ GB خام در سال است. با دو Replica، سه کپی زنده داریم؛ Backup جداست. Index و WAL را با یک ضریب جادویی دقیق حساب نکن؛ برای Schema و بار واقعی نمونه بساز و حجم را اندازه بگیر. متن فارسی در UTF-8 لزوماً یک Byte به‌ازای هر حرف نیست.

برای پهنای باند، «تعداد پاسخ در ثانیه × اندازهٔ پاسخ» را حساب کن. اگر پاسخ جزئیات ۱۰ KB باشد، ۱۱۶ پاسخ در ثانیه حدود ۱٫۱۶ MB/s بدنهٔ خروجی است؛ Header، TLS، فشرده‌سازی و تصویرها جدا هستند. تصویر از CDN می‌تواند بار Django را کم کند، ولی حجم دانلود کاربر همچنان وجود دارد.

## آزمایشگاه: ببین یک API چند Query می‌زند

در `lab` دو Model داریم: `Customer` و `Purchase`. سه خرید را برای یک مشتری می‌سازیم. در نسخهٔ ساده، هر بار دسترسی به `purchase.customer.name` یک Query دیگر می‌زند. نمونهٔ بهینه:

```python
from demo.models import Purchase
from demo.services import measure

slow = measure(lambda: [p.customer.name for p in Purchase.objects.all()])
fast = measure(lambda: [p.customer.name for p in Purchase.objects.select_related("customer")])
print(slow["queries"], fast["queries"])
```

برای سه رکورد، حالت اول ۴ Query و حالت دوم ۱ Query دارد. `select_related` برای رابطهٔ تک‌مقداری Join می‌سازد. اگر رابطهٔ چندتایی مثل اقلام سفارش باشد، `prefetch_related` معمولاً مناسب‌تر است. این انتخاب را از روی نوع رابطه انجام بده، نه فقط اسم «بهینه‌سازی».

`measure` زمان سپری‌شده و تعداد Query اتصال Primary را ثبت می‌کند. اندازه‌گیری یک بار روی SQLite یک Benchmark معتبر Production نیست؛ هدف دیدن اثر کد است. برای مقایسهٔ واقعی، Dataset، تعداد اجرا، Warmup و همزمانی را ثابت نگه دار. میانگین Query Time هم جای p95 زمان پاسخ HTTP را نمی‌گیرد.

## معیار تصمیم، نه حدس خرید سرور

اگر هدف ۲۰۰ درخواست بر ثانیه است و در آزمایش هر Worker فقط ۲۰ درخواست در ثانیه با p95 مطلوب پاسخ می‌دهد، تقسیم ساده ۱۰ Worker نقطهٔ شروع تخمین است. بعد محدودیت DB، CPU، شبکه و حافظه را بررسی کن؛ فرض استقلال کامل Workerها معمولاً درست نیست. هنگام قطع یک Node، ظرفیت باقی‌مانده هم باید هدف را پوشش دهد.

۹۹٫۹٪ موفقیت می‌تواند براساس زمان یا درخواست تعریف شود؛ این دو در ترافیک نامنظم یکسان نیستند. SLI مقدار اندازه‌گیری‌شده، SLO هدف داخلی و SLA تعهد رسمی‌اند. برای پروژهٔ تمرینی فقط تعریف عملیاتی مشخصی بنویس: مثلاً «۹۹٫۹٪ درخواست‌های معتبر زیر ۵۰۰ ms پاسخ موفق بگیرند».

## تمرین‌های تکمیلی و پاسخ

1. نرخ Write را دو برابر کن و Retention را نصف کن. حجم خام چه می‌شود؟ — ثابت می‌ماند، ولی بار نوشتن لحظه‌ای دو برابر است؛ Storage برابر به معنی ظرفیت برابر نیست.
2. Hit Rate از ۹۰٪ به ۵۰٪ می‌رسد. بار DB چه تغییری می‌کند؟ — برای همان ترافیک و یک Query به‌ازای Miss، پنج برابر می‌شود.
3. سه خرید را به صد خرید تبدیل کن. تعداد Query حالت ساده چیست؟ — ۱۰۱؛ حالت Join همچنان یک Query است، ولی حجم پاسخ و هزینهٔ Join بزرگ‌تر می‌شود.
4. عدد ۲۰۰ ms را برای Little's Law استفاده کن. — ۲۰۰ ms برابر ۰٫۲ ثانیه است؛ واحد را اشتباه وارد کنی، تخمین ۱۰۰۰ برابر خطا می‌کند.

**مرز آزمایش:** تست این فصل محاسبهٔ واحدها و تغییر ۴ Query به ۱ Query را بررسی می‌کند. از آن ظرفیت سرور یا SLA استخراج نشده است.

## شروع عملی این فصل

پوشهٔ `lab` همین فصل یک پروژهٔ مستقل است. فایل `lab/README.md` روش نصب و اجرا را توضیح می‌دهد. پس از نصب Django و اجرای Migration، دستور `python demo_script.py` مثال اصلی را با دادهٔ تمرینی اجرا می‌کند؛ `python manage.py test` هم تست‌های رفتاری را اجرا می‌کند. در این مسیر فقط محیط محلی استفاده می‌شود و حساب سرویس خارجی لازم نیست. کدهای Connector اختیاری در متن، نیازهای جدا دارند.

**نتیجهٔ بررسی:** 2 تست این فصل با SQLite پاس شده است. این نتیجه، عملکرد کلاستر، Provider واقعی یا تست همزمانی PostgreSQL نیست.
